**질문:** `ResetCycleState()` 상당의 리셋을 InspectionSequence 실행 스레드 밖(MainRun 폴링 스레드)에서 직접 호출해도 안전한가?

**조사 결과 — 리셋이 건드리는 상태를 3분류:**

1. `m_bCycleHasNG` / `m_bCycleDatumFailed` / `m_bImmediateFailSent` / `m_nCurrentZIndex` / `m_nLastZIndex`
   — 평범한 bool/int 필드. 찢어진 쓰기(torn write)는 없지만, 시퀀스 스레드가 `AddResponseV1Cycle`(1506번째 줄) 한복판에서 이 값들을 읽는 중에 다른 스레드가 0/false 로 덮으면 **그 사이클의 P/F 판정이 오염된다**(예: `m_bCycleHasNG` 가 지워져 NG 부품이 P 로 나감). 락은 없다.

2. `m_dicCrossZImages` (크로스-Z 이미지 저장소)
   — `_crossZImageLock` 으로 보호됨. `ClearCrossZImages()` 호출 자체는 스레드 안전. **단** 시퀀스 스레드가 z=1 role B 를 기다리는 중에 지워지면 크로스-Z Datum 검출이 그 사이클에서 실패한다(기능적 오염, 크래시는 아님).

3. `_datumTransforms`(Dictionary) / `_failedDatums`·`_alignFailedDatums`(HashSet)
   — **락이 전혀 없다.** 시퀀스 스레드가 `Action_FAIMeasurement` 의 DatumPhase 에서 `MarkDatumFailed`(Add) / transform 등록을 수행하는 동안 다른 스레드가 `Clear()` 를 부르면 .NET Dictionary/HashSet 은 내부 상태가 깨져 **무한 루프 또는 InvalidOperationException** 이 날 수 있다. 이건 실제 크래시 위험이다.

**결론 — 채택하는 안전 호출 방식:**
`ProcessReset` 은 각 InspectionSequence 에 대해 **`seq.State == EContextState.Idle` 인 경우에만** 리셋을 호출한다. Idle 이면 그 시퀀스 스레드는 명령 대기 루프에 있고 위 상태를 아무도 만지지 않으므로 MainRun 스레드의 단독 접근이 보장된다. Idle 이 아니면 **건드리지 않고 건너뛴 뒤 Error 로그 + ACK FAIL** 로 알린다.

**왜 Stop() 먼저 호출하지 않는가:** `SequenceBase.Stop()`(388번째 줄)은 `RequestPacket != null` 이면 `AddResponse()` 를 호출한다 — 즉 **PLC 가 요청하지도 않은 `$RESULT` 응답이 한 장 더 나간다.** 복구 명령이 오히려 프로토콜을 더 꼬는 부작용이라 채택하지 않는다. 실제 "꼬였을 때"는 사이클이 멈춰 있어 State==Idle 인 경우가 대부분이고, 정말 실행 중이라면 그 사이클이 끝난 뒤 PLC 가 `$RESET` 을 재전송하면 된다.

**왜 `_lastPrepZIndex` 는 무조건 리셋하는가:** `volatile int` 이라 어느 스레드에서 써도 안전하고, 0 은 "다음 $TEST 는 Datum(z=0)" 이라는 가장 보수적인 초기값이다. 정상 운전에서는 모든 `$TEST` 앞에 `$PREP` 이 선행해 이 값을 다시 덮으므로 부작용이 없다.

**`m_nLastZIndex = 0` 뒤처리:** `ResetCycleState()` 주석은 "호출 후 재산출 필요 — 호출부 의무" 라고 적혀 있으나, 이 리셋 경로에서는 **재산출하지 않는다.** 이 필드를 읽는 지점은 단 두 곳이고 둘 다 읽기 직전에 스스로 `ComputeLastZIndex()` 로 덮는다 — `AddResponseV1Cycle`(1517→1518번째 줄), `HandleDatumIndexResponse`(1529번째 줄). 따라서 0 인 상태가 판정에 관여할 수 없다. (재산출하려면 `recipeManager` 접근이 필요해 리스크만 늘어난다.) 이 근거를 신규 메서드 주석에 남긴다.

//    실행 중인 시퀀스는 손대지 않고 건너뛴다 — 조용히 넘기지 않고 Error 로그를 남겨 PLC 측 재전송 판단을 돕는다.
//  ▶ Stop() 을 먼저 부르지 않는 이유: SequenceBase.Stop() 은 RequestPacket!=null 이면 AddResponse() 를 호출해
//    PLC 가 요청하지도 않은 $RESULT 를 한 장 더 내보낸다 — 복구 명령이 프로토콜을 더 꼬는 부작용이라 미채택.
//  ▶ 반환값: 대상이 1개 이상이고 그 전부를 리셋했을 때만 true(=ACK OK). 부분 리셋은 클린 슬레이트가 아니므로 false.
private bool ResetSequenceCycleStates()
{
    int nFound = 0;
    int nReset = 0;
    int nCount = Sequences.Count;
    for (int i = 0; i < nCount; i++)
    {
        SequenceBase seqBase = Sequences[i];
        InspectionSequence inspSeq = seqBase as InspectionSequence;
        bool bIsInsp = inspSeq != null;
        if (!bIsInsp)
        {
            continue;
        }
        nFound++;

        bool bIsIdle = inspSeq.State == EContextState.Idle;
        if (!bIsIdle)
        {
            Logging.PrintLog((int)ELogType.Error,
                "[RESET] Seq={0} 실행 중(State={1}) — 상태 리셋 건너뜀(스레드 안전). 사이클 종료 후 $RESET 재전송 필요. //260807 hbk",
                inspSeq.Name, inspSeq.State.ToString());
            continue;
        }

        inspSeq.ResetCycleStateForProtocolReset();
        nReset++;
        Logging.PrintLog((int)ELogType.Trace,
            "[RESET] Seq={0} 클린 슬레이트 완료 //260807 hbk", inspSeq.Name);
    }

    bool bAllReset = nFound > 0 && nReset == nFound;
    return bAllReset;
}
