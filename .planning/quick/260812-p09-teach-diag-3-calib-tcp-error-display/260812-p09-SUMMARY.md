## 빌드 검증 스크립트 버그 발견 보고

Quick #2 가 이미 고친 `(set -o pipefail; msbuild | grep ... | head) || fallback` 형태도 여전히 틀렸다는 것을 이번 계획 수립 중 plan-checker 가 실측으로 발견했다. `-v:minimal -nologo`로 빌드하면 MSBuild 는 **"Build succeeded." 를 출력하지 않는다**(실제 출력은 산출물 경로 한 줄뿐). grep 이 아무것도 찾지 못해 종료코드 1 → `pipefail` 때문에 파이프라인 실패 → **빌드가 성공했는데도 폴백이 매번 돌고**, 폴백도 같은 이유로 무출력 → 성공/실패 구분 불가능한 상태가 된다.

해결: 파이프라인 종료코드 대신 **MSBuild 자신의 종료코드(`rc`)**를 성공 신호로 쓰고, 로그는 파일로 받아 별도 `grep`. 폴백 조건이 명시적(`rc != 0`)이라 죽은 코드가 될 수 없고, `BUILD_RC=`가 항상 출력되어 무출력 상태가 생기지 않는다. 추가로 스크래치 폴백의 `-p:OutputPath=` 스위치를 더블슬래시(`//p:`)에서 대시+백슬래시 경로(`-p:` + `C:\...`)로 교체 — Git Bash(MSYS)가 더블슬래시 스위치를 UNC 경로로 오인해 `MSB1001` 로 항상 실패하는 문제를 피했다. **이번 실행에서 두 태스크 모두 정상 경로(잠김 없음)로 1차 시도에 성공해 폴백 자체는 실제로 발동하지 않았지만, 스크립트 형태는 검증된 대로 그대로 사용했다.** 다음 Quick 에도 이 형태(`BUILD_RC=` 종료코드 판정 + `-p:`/백슬래시)를 쓸 것을 권장한다.

## 설계 판단과 근거

1. **헬퍼 1개 + 1줄 호출 vs 지점마다 6~7줄**: 후자는 diff 가 커져 "본문 동일성" 자동 검사(알림 호출 줄만 빼면 편집 전과 동일)가 사실상 불가능해진다. 헬퍼로 응집시켜 diff 를 1줄/지점으로 최소화했다.
2. **헬퍼를 `ProcessAlignCalib` 바깥에 배치**: 본문 동일성 검사가 메서드 시작~끝 구간만 잘라 비교하므로, 헬퍼가 메서드 안에 있으면 본문 자체가 늘어나 검사가 무의미해진다.
3. **`Application.Current` null 가드 추가**(형제 콜백엔 없음): 우리 알림 경로는 실패가 확정된 뒤에만 호출되는데, 이 시점이 앱 종료 처리 중과 겹칠 수 있어 더 방어적으로 가드를 뒀다.
4. **`Dispatcher.Invoke`(동기) 유지**: 사용자 지정 + 기존 성공 경로(`OnCalibStepViewer`/`OnCalibEndViewer`)가 이미 같은 동기 방식이고, 명령당 호출 빈도가 1회뿐이라 성능 부담이 없다.
5. **`lbl_calStatus` 색 미변경**: 이 파일에 `Text` 대입이 37곳(이번 +1)인데 일부만 `Foreground`를 칠하면 Quick #1 이 없앤 stale-색 버그가 재발한다.
6. **등급 `ETeachGrade.Bad` 고정**: 실패 전용 알림 경로라 점수가 없어 `ClassifyScore`를 적용할 수 없다.

## START 실패는 명령을 실패시키지 않는다

B 지점(`START: 모델 로드 실패`)은 로그만 남기고 `resultPacket.IsPass = true`로 START 자체는 진행한다(이 동작은 손대지 않았다). 화면에는 `✕ [자동] START 모델 로드 실패: ...`가 조기 경고로만 뜨고, 이후 STEP 에서 자연 실패하게 된다.
