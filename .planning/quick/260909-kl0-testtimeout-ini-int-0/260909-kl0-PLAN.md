플래너가 편집 전 직접 확인한 사실. 실행자는 **라인번호만 재확인**하고 결론은 그대로 쓰면 된다.

### A. 죽은 설정 — 제거 안전성 (요구사항 1)

1. **소비 코드 0건.** `grep -rn` (`--include=*.cs --include=*.xaml --include=*.ini --include=*.json`) 결과 매칭 3건: 선언 1줄(`WPF_Example/Setting/SystemSetting.cs:169`) + `WPF_Example/bin/x64/{Debug,Release}/Setting.ini` 2건. bin 아래 두 파일은 **git 미추적 빌드 산출물**이다(`git ls-files --error-unmatch` 실패 확인). 손대지 않는다.

2. **`Setting.json` 등 다른 직렬화 경로 없음.** `SaveToJson()` / `LoadFromJson()` 은 파일 하단(`:431~:448`)에서 **통째로 주석 처리**돼 있다. `SettingJsonFile` 필드(`:37`)도 그 주석 블록 안에서만 참조된다. 즉 INI 가 유일한 직렬화 경로다.

3. **INI 고아 키는 무해하다.** `Load()`(`:294~`)는 INI 키를 순회하지 않는다 — `GetType().GetProperties()` 로 **프로퍼티**를 돌면서 `loadFile[group][name]` 을 조회한다(`:301-302`). 속성이 사라지면 그 키는 읽히지 않고 그대로 방치된다. 예외도 나지 않는다.

4. **고아 키는 다음 저장에서 자연 소멸한다.** `Save()`(`:378~`)는 매번 `new IniFile()`(`:379`)을 만들어 현재 프로퍼티만 기록하고 `saveFile.Save(SettingIniFile)`(`:429`)로 파일을 덮어쓴다. 병합이 아니라 전체 치환이다.

5. **`[Category]` 그룹 상태머신 누출 없음.** `Load()`/`Save()` 의 `group` 지역변수는 `[Category]` 를 만날 때만 갱신되는 carry-over 방식이다. 삭제 대상 바로 다음 프로퍼티 `LightSettleMs`(`:174`)가 자기 `[Category("System|Enviroment")]`(`:173`)를 갖고 있으므로, 앞 프로퍼티(`ServerPortV1`, `[Category("Connection|Server")]` `:162-163`)의 그룹이 새어 들어갈 여지가 없다.

**→ 결론: `[Browsable(false)]` 대안이 아니라 속성 자체를 제거한다.**
근거: `[Browsable(false)]` 는 UI 에서만 감출 뿐 INI 직렬화는 계속되고 죽은 코드가 그대로 남는다. 코드베이스의 `MeasCorrectionFactor` 선례는 "값과 로직은 살아 있고 운용 정책상 숨김"이라 성격이 다르다(재노출 가능성이 설계에 포함돼 있다). 여기는 **소비자가 0**이라 숨겨도 되살릴 대상이 없다. 위 1~5 로 제거 위험이 없음이 확인됐다.

### B. int 로드 결함 — 원인과 파급 (요구사항 2)

- `Load()` `case "Int32":`(`:322-325`)가 `loadFile[group][name].ToInt()` 를 인자 없이 호출한다.
- `IniFile this[string section]`(`WPF_Example/Utility/Ini.cs:572`)은 섹션이 없으면 **빈 섹션을 새로 만들어 반환**한다 — 예외 없음.
- `IniSection this[string name]`(`Ini.cs:953`)은 키가 없으면 `IniValue.Default`(`Value == null`)를 반환한다.
- `IniValue.ToInt(int valueIfInvalid = 0)`(`Ini.cs:179`)은 변환 실패 시 `valueIfInvalid` 를 반환 → **0**.
- 그 0 이 `prop.SetValue` 로 코드 기본값을 덮어쓰고, 이어지는 `Save()` 가 0 을 디스크에 기록한다.

### C. `Load()` 재호출 경로 — 반드시 알고 갈 것

`Load()` 는 생성자(`:234`) 외에 **`WPF_Example/UI/Setting/SettingWindow.xaml.cs:26`(`pSetting.Load()`)에서 설정창을 열 때마다 다시 호출된다.**

권장 수정(`prop.GetValue(this)` 를 fallback 으로 전달)을 적용하면 이 재호출 시 보존되는 값은 "코드 기본값"이 아니라 **그 시점의 메모리 값**이다. 이 동작이 타당한 이유:

- 현행 코드에서는 같은 상황에서 그 값이 **0 으로 초기화된다**. 즉 "INI 에 키가 없는 int 설정은 설정창을 열기만 해도 0 이 된다"는 잠복 결함이 이미 있다. 메모리 값 보존은 그보다 항상 안전하다.
- INI 에 키가 있는 정상 상태에서는 INI 값이 그대로 이긴다 — 동작 불변.
- 한 번 `Save()` 하고 나면 모든 int 키가 파일에 존재하므로 이 경로는 과도기에만 의미가 있다.

### D. 읽기 전용 int 프로퍼티 — 동작 불변 확인

`WPF_Example/Custom/SystemSetting.cs:109 PickerCalRequiredSteps` 는 **getter 만 있는 `int`** 프로퍼티다. 현행에서도 `prop.SetValue` 가 예외를 던지고 `Load()` 의 `try/catch`(`:365-367`)가 로그만 남기고 삼킨다. 수정 후에는 `prop.GetValue(this)` 가 먼저 실행되는데 getter 가 존재하므로 정상 반환하고, `SetValue` 에서 기존과 **동일하게** 던진다. 새 예외 경로가 생기지 않는다.

### E. `AfterLoad()` 복원 가드와의 상호작용 — 건드리지 말 것

`Custom/SystemSetting.cs:119 AfterLoad()` 의 `RestorePcRoleDefault`(`PcRole == 0` → 1), `RestoreAlignVerifyDefaults`(`KeepDays <= 0` → 기본) 등은 **그대로 둔다**.

- 키 부재 시: 이제 0 이 아니라 코드 기본값이 들어오므로 가드는 조건 불성립 → no-op. 결과값 동일.
- 키가 있고 값이 0 인 경우: 기존과 100% 동일하게 가드가 복원한다.
- 가드를 지우면, 이미 0 이 기록돼 있는 기존 INI 에서의 복원 동작이 사라진다 → **회귀**. 삭제 금지.

### F. 범위 밖이지만 같은 결함이 있는 곳 (기록만, 수정 금지)

- `case "Double":`(`:327-329`) — `IniValue.ToDouble(double valueIfInvalid = 0)`(`Ini.cs:276`). 동일 결함. 실제로 `RestoreEthernetVisionDefault` / `RestoreCalibSearchDefault` / `RestoreAlignVerifyDefaults` 가 항목별로 땜질 중이다.
- `case "String":`(`:330-336`) — `IniValue.ToString()`(`Ini.cs:317`)이 `Value` 를 그대로 돌려주므로 키 부재 시 **null** 이 대입된다. `RestoreDataPathDefaults` 가 땜질 중. 덤으로 `isDirectory == true` 인데 값이 null 이면 `Directory.CreateDirectory(null)` 이 예외를 던지고 `try/catch` 가 삼킨다.
- `case "Boolean":`(`:337-340`) — **의도된 하위호환 설계**(`:182`, `:191`, `:198` 주석에 명시). 절대 손대지 않는다.
