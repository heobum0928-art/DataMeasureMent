<investigation_findings>
아래는 플래너가 코드로 직접 확인한 사실이다. 실행자는 이 판단을 그대로 따르되 라인번호만 재확인한다.

## 1. 가로/세로 방향은 "추측"이 아니라 변수에서 그대로 나온다 (이 작업 최대 난점 해소)

오케스트레이터가 지목한 위험은 `MainView.xaml.cs :1389` 가 접미사를 **화면 토글**(`_currentImageSource`)로
정한다는 점이다. 자동 검사에는 그 토글이 없다. 결론: **토글을 흉내내지 않는다. 검출이 실제로 소비한
변수에서 방향을 가져온다.** 근거 체인(전부 코드 확인):

| 단계 | 코드 | 사실 |
|------|------|------|
| ① | `ProcessDatumDualImage` :330 | `TryGrabOrLoadDualDatumImages(..., out imgH, out imgV, ...)` — 이후 검출은 imgH=가로축, imgV=세로축으로 소비 |
| ② | `TryGrabOrLoadDualDatumImages` :1078~1080 | `imageHorizontal = result.Horizontal; imageVertical = result.Vertical;` |
| ③ | `TryTakeCrossZImageClones` :1215~1216 | `result.Horizontal = TakeCrossZImageCopy(keyA); result.Vertical = TakeCrossZImageCopy(keyB);` |
| ④ | `ResolveCrossZDatumRoleKeys` :1191~1192 | `keyA = base + "_ZA"`, `keyB = base + "_ZB"` |
| ⑤ | `CaptureAndStoreCrossZDatumImage` 호출부 :1131~1132 | `bIsRoleA = (nCurZ == datum.ZIndexA)`, `bIsRoleB = (nCurZ == datum.ZIndexB)` |
| ⑥ | `TryLoadStaticDualDatumImages` :1091~1092 | 정적 경로도 `pathH = TeachingImagePath`, `pathV = TeachingImagePath_Vertical` |
| ⑦ | `GrabOrLoadCrossZRoleImage` 주석 :926~927 | "role A ↔ TeachingImagePath, role B ↔ TeachingImagePath_Vertical" (기확립 규약이라고 명시) |
| ⑧ | `MainView.GrabSaveAndDisplay` :1483~1490 | 수동 저장 write-back: 세로 토글 → `TeachingImagePath_Vertical`, 그 외 → `SetLatestImagePath`(=TeachingImagePath) |

**확정: `ZIndexA` = role A = `imgH` = `_horizontal` = `TeachingImagePath`,
`ZIndexB` = role B = `imgV` = `_vertical` = `TeachingImagePath_Vertical`.**
자동채움은 `imgH`/`imgV` 변수를 그대로 각 접미사에 대응시킨다 — 조건 분기가 아예 없으므로 뒤바뀔 수 없다.

## 2. 새로 grab 할 필요 없다 — Shot 은 추가 복사조차 0회

`MeasureShotFaiList` :568~572 가 이미 Shot 당 1회 `sharedSrc = new SharedHImage(image.CopyImage())` 를
만들고, :586 `QueueSharedShotOrigin(sharedSrc, parentSeq2)` 가 그것을 비동기 큐에 넣는다.
자동채움은 **같은 `sharedSrc` 에 `AddRef()` 한 번 더 하고 큐에 한 건 더 넣을 뿐**이다. 추가 메모리 복사 0.

Datum 은 공유 사본이 없고 `img`/`imgH`/`imgV` 가 호출부 `finally` 에서 즉시 Dispose 되므로
**`CopyImage()` 1회가 반드시 필요하다.** 소유권을 넘기는 방식(=Dispose 를 조건부로 만들기)은
과거 `AccessViolationException` 을 낸 바로 그 패턴이므로 금지. 설정 ON 일 때만 발생하는 비용이고,
설정 OFF 면 `bool` 검사 한 번으로 끝난다.

## 3. 검사 스레드에서 동기 디스크 I/O 를 완전히 없앨 수 있다

`CaptureImageSaveService.SaveRequest` :316~321 은 이미 `DirectoryOverride` 를 지원하고
`Directory.CreateDirectory(baseDirectory)` 를 **워커 스레드에서** 호출한다.
따라서 경로 계산 함수는 폴더를 만들 필요가 없다 — 순수 문자열 계산으로 만든다.
수동 [검사Grab] 쪽도 `MainView.GrabSaveAndDisplay` :1443 이 저장 직전에 스스로 폴더를 만들고 있어
(`if (!Directory.Exists(dir)) Directory.CreateDirectory(dir);`) 폴더 생성을 빼도 안전하다.
`Action_FAIMeasurement` 에는 `lock` 이 하나도 없다(grep 확인) — "락 쥔 채 저장" 위험은 구조적으로 없다.

## 4. 포맷: bmp 를 강제해야 한다 (기존 설정에 얹으면 안 된다)

`SaveRequest` :330~334 는 origin 을 `SystemSetting.OriginImageFormat`(JPG/BMP)으로 쓴다. 기본값은 JPG다.
검사이미지는 라이브 grab 을 그대로 대체해야 해서 손실압축 불가이므로 **요청 단위 포맷 오버라이드**를
추가한다(비어 있으면 기존 규칙 그대로 = 회귀 0). PNG 는 CXP 13376×9528 에서 DEFLATE 자체가 tact
병목이라 260716 에 bmp 로 전환한 결정이므로 되돌리지 않는다.

## 5. 저장 대상 게이트 — "라이브로 방금 찍은 이미지"만 채운다

| 경로 | 이미지 출처 | 자동채움 |
|------|-------------|----------|
| SIMUL_MODE 빌드 | 저장 파일 로드 | **안 함** |
| OfflineInspectMode ON | 저장 파일 로드 | **안 함** (읽은 파일을 자기 자신에게 되쓰는 왕복) |
| 실기 Shot grab (`AcquireShotImage` else 분기 :464~471) | 라이브 촬영 | 함 |
| 실기 Datum 1-image (`GrabOrLoadDatumImage` :985~1002) | 라이브 촬영(이 분기는 항상 grab) | 함 |
| 실기 크로스-Z Datum (`bCrossZEnabled`) | role A/B 모두 라이브 촬영 | 함 |
| 정적 2장 Datum (`TryLoadStaticDualDatumImages`) | 기존 티칭 파일 로드 | **안 함** (되쓰기) |

마지막 행 때문에 `TryGrabOrLoadDualDatumImages` 에 `out bool bCrossZLiveCaptured` 를 하나 추가한다
(값 = 이미 계산돼 있는 `bCrossZEnabled`). 조건을 호출부에서 다시 계산해 복제하는 것은 금지(D-09).

## 6. 경로 write-back — 한다. 단 값이 다를 때만, 레시피 저장은 절대 자동 트리거 금지

수동 [검사Grab] 은 저장 후 노드 경로를 갱신한다(`InspectionListView` :1219/:1225 주석 "write-back →
PropertyGrid 갱신"). 자동채움이 write-back 을 생략하면 **경로가 비어 있는 새 레시피에서는 파일만
쌓이고 아무도 그것을 가리키지 않아** 이번 작업의 목적(수동 버튼 대체)을 달성하지 못한다.

정책:
- 파일명이 노드 이름에서 결정론적으로 나오므로 **현재 값이 이미 같은 경로면 아무것도 하지 않는다**(대부분의 사이클).
- 다르거나 비어 있을 때만 대입하고 Trace 로그 1줄을 남긴다(“레시피 저장은 사용자가 직접”).
- **`RecipeFiles.Save`/레시피 저장은 호출하지 않는다.** 사용자 의도 없이 레시피를 쓰지 않는다.
- 알려진 한계: write-back 은 비동기 write 완료 **전에** 일어난다. 워커가 쓰기 전에 앱이 죽으면 노드가
  없는 파일을 가리킨다 → 오프라인 검사에서 "파일 없음" 로그 + NG 로 **시끄럽게** 드러난다(조용한 오검 아님).
  이 실패 모드를 SUMMARY 에 기록할 것.

## 7. 덮어쓰기 정책 (요구사항 5 — 명시적으로 기록)

매 사이클 같은 노드는 **같은 파일명을 덮어쓴다.** 이것이 의도다 — 이 파일은 히스토리가 아니라
"이 노드의 현재 오프라인 검사이미지" 한 장이고, 목표가 "마지막으로 검사 진행한 이미지로 채우기"이기
때문이다. 결과 이미지 히스토리는 기존 origin/capture 트리(`ResultSavePath\Image\yyMMdd\HHmm\...`)가
그대로 담당하며 이번 변경의 영향을 받지 않는다. 파일 수는 노드 수만큼으로 고정(무한 증가 없음).

알려진 한계(수동 [검사Grab] 에서 그대로 상속): 파일명에 시퀀스명이 없어 서로 다른 시퀀스가 **완전히
동일한** ShotName/DatumName 을 쓰면 충돌한다. 이는 현재 수동 경로도 동일하며, 파일명 규약을 바꾸면
오프라인 검사가 파일을 못 찾으므로 **바꾸지 않는다.** SUMMARY 에 한계로 기록만 한다.
